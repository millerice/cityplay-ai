# Architecture Decisions

2026-10-14，依据真实 PoC；详见 [能力报告](qloo-capability-report.md)。

## ADR-001 — 演示城市

纽约及明确半径周边作为 V1 主演示区域候选，上海保留实验支持。纽约音乐兴趣样本的场所类别及营业表更适合当前闭环；上海酒店占比高、小众类别候选较弱。此结论来自小样本，不是全城覆盖保证。

`New York, NY` 实测解析为纽约州，不能直接作为城市硬过滤。实现时必须核验解析地理范围，优先使用确认的 locality ID 或明确坐标与半径；边界不明则询问用户，不能静默扩大范围。20km 坐标实验返回的地点距离均符合范围；书店样本含 Hoboken，UI 必须明确“附近”，若要求严格市内则另核验行政边界。

## ADR-002 — 数据职责

Qloo 负责文化关联与地点候选；营业现状、活动场次、预算和公众可访问性需要独立核验。兴趣信号不会自动保证场所类别。允许缺失字段和数据不足结果，禁止编造营业、价格或路线距离。

先按硬约束过滤，再以同次请求内相对亲和、类别多样性与证据质量决策；不将 affinity 当作个人概率，不先设计固定加权公式。

## ADR-003 — 服务端适配

PoC 使用官方 Harness 0.1.26 和指南支持的原始 GET。V1 可优先评估服务端直接 HTTP，保留顶层 location、地理解析与 rate-limit headers；Harness compact 结果丢弃坐标。所有 Key 留在服务端，固定赛事地址，禁止跨 origin 重定向、静默换环境或虚构降级。

## ADR-004 — 证据与公开仓库

官方指南禁止公开存储真实响应；本地证据放在 `.qloo-private/`，公开 fixture 使用明确标记的合成数据。文档记录方法、统计、结构和局限，不复制完整地点实体数据。

## 下一阶段

阶段 1 核心能力可继续；暂不创建 Web 脚手架。接下来确认合法地点核验来源和部署方式，再实现“兴趣消歧 → Qloo 候选 → 类别/位置过滤 → 现实核验 → 3 个建议”的可追溯单 Agent 闭环。需另测缓存、并发额度保护、429/5xx/超时和评审后 Key 失效处理。

## ADR-005 — 阶段 2 实现（2026-10-14）

用户选择 DeepSeek v4，并授权 Pro/Flash 自行选用。已实现 Python 标准库服务核心及 CLI：Pro 解析意图并完成真实 Qloo 地点链路，另验证当前 Flash 模型能提取预算、时间和即时营业约束。请求/回报模型名均保留，不假定旧 v4-flash 标识仍对应旧模型。

第三方核验目前仅检查 Qloo 列出的网站可达与名称对应，且实行公网 DNS 检查和 TLS IP 固定。尚未核验分店、营业/活动/预算/公众访问；因此输出 partial，未知硬约束拦截候选，状态使用 CANDIDATES_CHECKED。地图、公共网站和部署留待阶段 3；参见 [阶段 2 验证](stage2-validation.md)。

## ADR-006 — 阶段 3 本地 Web MVP（2026-10-14）

保留 Python 核心，采用本地标准库服务加 buildless HTML/CSS/JS 界面，无新增运行时依赖。先解析、编辑确认，再检索；同名候选必须选择，换一批排除当前需求已展示 ID。后台异步任务提供实际进度，浏览器只接收呈现所需数据；全部 Key、原始证据和安全错误存储留在服务端。

此轮仅本地验证；未注册或发布 Sites。服务器默认仅 127.0.0.1，提供会话、CSRF、任务隔离与进程预算保护。桌面/移动端真实浏览器验收完成，详见 [阶段 3 验证](stage3-validation.md)。地图与严格行政范围仍未实现，公众部署与持久全局限额留到后续阶段。
