# 首次使用走查：问题与优化顺序

日期：2026-10-15。使用当前本地预览，以没有已保存兴趣、没有预填输入的新页面开始，检查 1280×900 桌面与 390×844 手机视口。使用实际 Qloo / DeepSeek 链路；测试期间添加的单项兴趣已经取消。未修改产品代码。

这是开发者代理进行的启发式走查和功能验收，不是陌生真人研究。以下明确区分已复现行为、代码检查和待验证的产品判断；不计算虚构的易用性分数、转化率、满意度或留存率。浏览器工具和观察带来额外耗时，因此不把整轮走查耗时当作应用性能数据。

后续修复与验收见 [修复记录](usability-repair-validation.md)。本文保留修复前观察。

## 判断

主链路可用、数据来源可追溯；但新访客仍需要理解过多内部概念，结果不足以解释“为什么值得我去”。应优先修复失败后的恢复能力，再收敛首页、搜索和版本解释，而不是继续增加入口与类别。

## 必须先修复

### A01：无结果时两个恢复按钮失效（已复现）

复现：选择一个实际文化起点 → 上海 → 画廊 → 无结果 → 点击换场所/调范围。

实际 DOM：`manual-entry.open=true`，范围设置也能变成 open，但父层 `manual-entry` 的计算样式仍为 `display:none`，body 仍有 `showing-results`。原因是结果页 CSS 隐藏整个手动入口，按钮只打开 details，没有退出结果模式。页面顶部“修改口味”能返回，说明已有可工作的恢复路径，应统一复用。

建议：统一返回编辑状态的函数，保留兴趣和条件；空结果直接给可点选的替代类别/范围，避免让人重新找表单。验收必须覆盖按钮实际可见和可操作，不能只断言 details.open。

代码检查另发现 `editRequest()` 引用了没有声明的 `review`，相关入口存在 ReferenceError 风险；本轮未逐一触发这些入口，不与上述已复现问题混为同一证据。

### A07：无结果提示需要对应实际原因（已复现）

预算20美元、必须现在营业的复测中，后端记录10个候选、3个类别不匹配，实际检查的6个地点分别命中 budget_unverified 和 open_now_unverified。系统没有将它们误报成满足条件的推荐，这是正确行为。但界面仍建议换场所或扩大范围，并不能解决营业与价格未核实的问题。应告知“找到了候选，但暂时无法核实这两项要求”，让用户明确选择保留硬要求、补充可信来源，或改为出发前自行确认的探索候选；不能自动取消约束。

## 下一轮最值得做的五件事

### A02：首页只保留一条主要路径（已观察＋设计建议）

文化卡片、领域、搜索、发现更多、城市、范围、场所、排除、兴趣库、每轮起点、猜你喜欢、手动输入叠在一起。虽然都能解释，却要求用户先理解产品结构。

建议：把“选一个起点 → 选择城市 → 看两个方向”作为默认路径。选好一个对象后，在手机可见位置提供行动按钮；范围、排除和完整兴趣库默认收起。猜你喜欢移到搜索附近，为不知从何开始的人提供即时帮助。验收目标是减少首轮决策，不是机械删掉必要条件。

### A03：把搜索匹配与相关发现分开（已观察）

迈克尔杰克逊搜索中混排其他艺人及电影，容易让人觉得系统答非所问。所有结果来自真实 API 不等于都准确回答了输入。

建议：仅基于实际规范名和已验证别名，将候选分为“可能就是你找的”“其他相关候选”。首屏优先明确匹配；找不到明确匹配要直说。其他候选折叠，不静默替换输入。不能仅靠语言模型宣布两个对象是同一身份。

### A04：首页发现流与查询缓存分离（已观察＋代码检查）

缓存来源、名称排序和过期策略目前影响首页内容。本轮首页出现之前 Daft Punk 查询中的小众相关对象；它们不是新访客的个性化结果。`LibraryStore.browse` 按领域、名称交错，并未为首页单独维护编辑候选集合。

建议：保留查询缓存，同时增加明确的发现候选身份与排序；初始展示更容易识别、文化背景更分散的样本，不把缓存新鲜度当兴趣相关性。缓存到期时提供可继续的初始内容，不让新访客先学会维护内容库。图片/封面需先核实来源、可用性和授权，不能自行补造。

### A05：版本要解释“我会体验到什么”（真实结果＋主观判断）

本轮路径确实改变了地点，但 MJ → 徐誉滕 → 星巴克未自然构成容易理解的“另一种人生”。这是产品吸引力判断，不据此断言 Qloo 关联错误或地点不真实。

建议：版本卡直接展示实际文化桥梁、场所类型组合，以及有来源支持的一句地点特点。让用户在多个真实关联起点中选一个愿意尝试的；如果无法解释差异，降低“人生”的承诺。不能把实体贡献分包装成人格或喜欢概率，也不能编造“同样复古”“一定安静”等氛围理由。

### A06：把地点选择变成可行动的决策（已观察）

现在能看名称、地址、距离、网站、地图，但地点简介主要在地图弹窗，两个地点的“为什么推荐”过于相似。新访客难比较、难出发。

建议：在卡片直接露出简短地点简介、已知特点和本轮推荐依据，分开呈现“文化关联”“地点事实”“尚需确认”。提供外部地图导航和地点收藏；用现有坐标生成导航入口即可，不必先做复杂路线规划。营业、门票和预约仍需独立来源，不能暗示已经核实。

## 补充评估维度

| 因素 | 当前证据或局限 | 可验证的优化方向 |
|---|---|---|
| 空间语义 | 默认纽约下城示例中心，“附近”不是设备定位；入口主区不显示中心解释 | 直接标注示例中心，允许城市内选区域；定位必须由用户主动触发 |
| 条件控制感 | 冲突问题用复选框，勾选含义不直观；两个入口还各有一组设置 | 城市冲突改成纽约/上海选择，统一条件来源，修改后给明确摘要 |
| 等待与恢复 | 熟悉版已显示时邻近版仍在请求，进度仍是通用兴趣检索文案 | 告知正在生成哪个版本、允许先用现有结果，提供取消/重试 |
| 语言与可读性 | 中文界面含英语地点简介、许多小号说明文字 | 可溯源翻译并可看原文；减少术语，真人抽测字号、对比度与理解程度 |
| 键盘和辅助技术 | 动态列表重建导致焦点回BODY；状态区已有role=status是优点 | 保持按钮/焦点稳定，验证Tab顺序、读屏播报和地图替代列表 |
| 用户反馈与回访 | 兴趣持久化，地点反馈仍限会话；无长期地点收藏/体验记录 | 区分“这次不想去”和“体验后不喜欢”，可撤销反馈；再验证长期学习 |
| 数据生命周期 | 目录1小时、快照5分钟；选择持久化；发布仍暂缓 | 返回用户不用重新选；公开部署前解释保存位置、清除方式及授权边界 |
| 文化覆盖与偏差 | 地区覆盖不均，编辑起点与关联对象有选择偏差 | 按地区/语言分层测可用率，展示覆盖边界；不把无结果当作用户兴趣无效 |
| 赛事可见价值 | 文化桥梁、解释和类别基线都存在，但主要藏在折叠区 | 在核心结果里用一条实际证据链展示Qloo的作用，深入技术细节再折叠 |

## 下一轮验收方式

先修复恢复按钮、按原因引导和焦点，再重排首页、精确/相关搜索与版本摘要。随后邀请少量未参与开发的人完成相同任务：选一个真喜欢的对象、找到一个愿意去的地方、说清推荐理由、在无结果时自行恢复。

记录真实任务完成、误点、求助、等待中断，以及用户自己的解释；“愿不愿意去”和“为什么相信”优先于泛泛评分。再让用户实际体验后反馈，才能讨论喜好准确性。单次走查与API候选重合率都不能代替这些证据。
